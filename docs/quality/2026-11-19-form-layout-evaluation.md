# Form layout evaluation — 2026-11-19

Read-only analysis of all existing forms, made for UX-06 (KAN-96) after UX-02. Line numbers refer to branch `pantryflow/ux-02-pantry-search` at `c959e0e`, which is identical to main for every file here except the Pantry tab. dp means React Native units. Not verified on a device unless stated.

Device confirmation since the analysis (2026-11-19): on the owner's phone, the add button on the Pantry tab sat behind the keyboard (the same mechanism as H1). UX-02 fixed it there with `hooks/useKeyboardOverlap.ts`.

Shared components (facts): `Input` wrap marginBottom md 12, label typography.label/textMuted mb xs 4, input minHeight 48, error under input (mt xs, small, danger) in an always-mounted live region (`components/Input.tsx:42-64`, `InlineError.tsx:14-19`). `Button` height 48, no outer margin, label typography.heading, variants primary/secondary/danger (`Button.tsx:75-83`). `OptionChips` is a horizontal ScrollView, row paddingVertical xs, chip paddingH md / paddingV sm, marginRight sm (+ gap sm) (`OptionChips.tsx:55-62`).

## 2. Inconsistencies

### High
H1. Android edge-to-edge keyboard can hide the primary action on add-item, edit-item, shopping-item and (less likely) login/register. `app/add-item.tsx:67-70`, `edit-item/[id].tsx:135-138`, `shopping-item/[id].tsx:113-116`, login/register 45-48/61-64: KAV `behavior={Platform.OS==='ios' ? 'padding' : undefined}` means NO avoidance on Android, and SDK 58 edge-to-edge does not resize the window, so the ScrollView viewport extends beneath the keyboard and short content does not scroll. add-item has autoFocus (86) and Save sits below two chip rows (matches the CI emulator observation); edit-item Save and Delete sit even lower. The one working mechanism in the repo, `hooks/useKeyboardOverlap.ts`, is used only by the pantry list (index.tsx:37, 183).
H2. Register "Check your email" view: 0 dp between message and first button (`register.tsx:53-54`) and 0 dp between the two buttons (54-55). Verified: container (126-131) has no `gap`, Buttons have no outer margin. Effect: two 48 dp primary buttons touch, a mis-tap risk and a visually broken block. Also two equally weighted primary buttons with "Go to sign in" before "Resend" (opposite order to confirm-email.tsx:50-52 and callback.tsx:50-52).
H3. Missing-item states (edit-item 76-88, shopping-item 65-79): error Text touches the Retry button (0 dp), and `alignItems:'center'` makes both Buttons content-width instead of full width, unlike every other screen's actions; Retry-to-Back gap is 16 (marginTop lg) rather than 12. Buttons are visually fine functionally but the layout is a third pattern. Rated High only for the 0 dp text/button contact; the rest is Medium.

### Medium
M1. Container padding differs in three flavours: auth forms 24H / 32T / 24B via per-side props (login 106-111, register 126-131); confirm-email and callback `padding xl, paddingTop xxl` (59/60), same values; modal forms 24 all round / 32 bottom (add-item 138, edit 236, shopping-item 168). Visible effect: modal titles start at 24 dp, auth titles at 32 dp; bottom 24 vs 32.
M2. Title-to-content spacing: 24 (auth forms: login 115, register 135), 12 (gap-based confirm-email/callback), 16 (modal forms 142/247/179). Three different values for the same title.
M3. Action blocks: login/register one primary button mt 12; confirm-email/callback two stacked full-width primary buttons gap 12 with no secondary variant (the second action "Go to sign in" is styled as primary, competing with Resend); add/edit/shopping-item use a Cancel|Save row (secondary left, primary right) with a spacer View; register confirmation stacked 0 gap. There are three action-block patterns plus the centered missing-item pair. The auth two-button blocks should use primary + secondary (callback, confirm-email, register view).
M4. Spacing source mixed: gap (confirm-email, callback, shopping addBar, noMatch) vs per-element margins (login, register, add-item, edit-item, shopping-item) vs an inline `<View style={{height:12}}/>` and `<View style={{width:12}}/>` spacers (add-item 101,121; edit 191,211; shopping-item 143). Spacer Views are the same value as spacing.md but are code smell.
M5. confirm-email double spacing: Input wrap mb 12 plus container gap 12 gives 24 dp below the field before the sent-message/button, vs 12 + marginTop 12 = 24 on login (coincidentally equal) but 12 only on shopping-item (Input -> actions uses actions mt 24; i.e. 12 + 24 = 36). Field-to-actions distance is 24 (login/register, confirm-email) vs 36 (add/edit/shopping-item, because Input mb 12 + actions mt xl 24; add-item/edit-item after chips: chip padding 4 + 24 = 28).
M6. Section label spacing within edit-item is internally inconsistent: Input -> "Status" 12+12 = 24; Status row -> "Category" 12; chips -> "Location" 12 spacer + 12 marginTop = 24 (edit 249-254, 191). add-item has no label marginTop: Input -> "Category" 12, chips -> "Location" 12 (spacer) (add-item 144-148, 101). Same labels, different gaps between add-item and edit-item.
M7. Status pills in edit-item are a hand-rolled control (158-180) beside the shared OptionChips; paddingV 12 => about 40 dp tall (<48 dp), no accessibilityRole/state, while `components/StatusSelector.tsx` has radio roles (71-90).
M8. add-item load-error block (76-77): screen-level InlineError with no style (so default Text, no danger color unless InlineError's Text receives style; style is undefined) followed by a primary Retry button with 0 dp between title, error and button.
M9. Resend-confirmation link on login (93-97) follows the sign-up row with 0 margin, centered link text only ~18-20 dp tall (<48 dp target); link targets on login/register (88, 113) are also small.

### Low
L1. Chips (OptionChips 56-62) are ~34 dp tall (padding sm 8x2 + label 13 line-height ~16-17); below 48 dp. They have no accessibilityRole/selected state (35-47).
L2. shopping.tsx add Input (125-141) has no label/accessibilityLabel (placeholder only) while all other fields have labels; search has an explicit accessibilityLabel.
L3. Only login/register/add/edit/shopping-item pass `announceKey`; confirm-email's Input (47-48) does not, so a repeat identical failure is not re-announced.
L4. callback working state: ActivityIndicator is left aligned below the title (48), vs centered spinners elsewhere.
L5. Safe-area handling differs: auth screens use SafeAreaView; modal forms do not (rely on the Stack header and sheet presentation); settings uses `edges=['bottom']`. The modal bottom inset on gesture-nav devices is not handled by the form (check on device).
L6. Dead style: `switchText` reused for the register confirmation message (register.tsx:53) instead of a `message` style as in confirm-email/callback.
L7. Button style prop in missing states mixes marginTop with centered layout; `errorText` is declared three times (edit, shopping-item, shopping tab).
L8. shopping addBar uses `alignItems:'flex-start'`; when an add error appears the Input grows by ~20 dp while the Button stays top-aligned (acceptable) but the 72 dp minWidth button label is typography.heading 18 (large for inline row).

## 3. Proposed common layout convention

Fits tokens and the majority pattern (auth: 24/32/24 container, title 26, buttons full width, controls 48 dp):

- Container: horizontal 24 (xl), top 32 (xxl), bottom 32 (xxl) for scrolling form screens (auth and modals); `backgroundColor: colors.bg`; SAV on auth, none on Stack-header modals. Modal screens may keep top 24 because the header supplies space (document as the one exception: top 24 when a native header is shown, 32 otherwise).
- Title: typography.title, marginBottom xl 24 (auth majority) for every screen; for modals change from lg 16 to xl 24.
- Body text: typography.body / textMuted, 12 (md) above the next control, 24 (xl) from the title (via title mb) only when the body follows the title; i.e. title mb 12 when a message follows, 24 when a field follows. Simplest: title mb md 12 with message, xl 24 with field; implement through a `title` style plus a `message` style with `marginBottom: md`.
- Field spacing: use Input's built-in mb 12 only; no extra gap or margin around Inputs. Section label: typography.label/textMuted, marginBottom xs 4, marginTop 0 (the preceding control provides 12; chip rows add xs padding). Between chip groups use one 12 dp separator only (via label marginTop md and remove the spacer Views).
- Action block: full-width Buttons, wrapper style `{ marginTop: xl (24), gap: md (12) }` after the last field (Input mb 12 + 12 = 24 effective; chip groups add 4). Two actions in a form that can be cancelled: row, secondary (Cancel) left, primary right, flex 1 (current modal pattern). Two actions that navigate (confirm-email, callback, register confirmation, missing states): stacked, primary first (the recovery/resend action), secondary second (back to sign in), gap 12. Destructive: danger variant below the primary block with marginTop xl, alone.
- Errors: field-level via Input `error` for validation/submit failures; screen-level InlineError (with a danger/small style) placed directly above the action block with mb sm 8 only for non-field errors; always `announceKey` on failures.
- Loading/disabled: `loading` on the primary action only; other actions disabled while busy (existing).
- Keyboard: one shared behavior. Reuse `useKeyboardOverlap` (bottom padding on the ScrollView content, `paddingBottom: base + overlap`) on every screen with inputs, instead of relying on KAV on Android; keep KAV 'padding' on iOS; `keyboardShouldPersistTaps="handled"` (already). Alternative with fewer moving parts: place Save/Cancel outside the ScrollView in a footer that is lifted by the overlap.
- Small targets: wrap links in Pressable with minHeight 48 (`hitSlop`/padding), chips/pills paddingV so total >= 48 or hitSlop with `accessibilityRole`/`accessibilityState`.

### Reusable pieces (>= 3 screens each)
1. `FormActions` (or exported styles `formActions`): stacked and row variants with fixed gap 12 and marginTop 24. Needed by register confirmation, confirm-email, callback, add-item, edit-item, shopping-item, both missing states (>= 3). Removes spacer Views and the 0 dp defects.
2. `FormScreen` styles object in `lib/theme.ts` or a small `components/FormScroll.tsx` (SV + padding + keyboard overlap, title style): login, register, confirm-email, add-item, edit-item, shopping-item (6 screens), fixes H1 and M1/M2 once.
3. `MissingState` (message + Retry + Back, full width, gap 12): edit-item and shopping-item (2 screens only; below threshold, so just fix both with the shared style from 1, plus the shopping tab's centered error block which is a third user: centered message + Retry).
No new dependencies.

### Smallest change per screen
- login: bottom/top stay; resend link minHeight 48 (or add Pressable padding); optional add `useKeyboardOverlap` bottom padding.
- register form: same as login (overlap padding).
- register confirmation: add container `gap: md` and message mb (or reuse confirm-email styles); order Resend first (primary) then "Go to sign in" as `variant="secondary"`; wrap in the same SAV/SV as confirm-email.
- confirm-email: remove double gap (container gap 12 and Input mb 12) by wrapping Input in a View with `marginBottom: -spacing.md`, or switch container from gap to per-element margins; make "Go to sign in" secondary; add `announceKey`.
- callback: make "Go to sign in" secondary; center the spinner (`alignSelf: 'center'` or wrapper) for visual parity.
- add-item: title mb 24, container padding top 32 only if no header; replace spacer Views with label `marginTop: md`; unify actions style; keyboard overlap padding or footer; give the load-error InlineError a style and 12 dp gap to Retry.
- edit-item: same as add-item; align label margins (all section labels marginTop 12 and remove spacer View) ; replace the status pill row with 48 dp targets (paddingV 16 / minHeight 48) and roles; actions style.
- shopping-item: title mb 24; actions style; Remove below.
- missing states (edit, shopping-item, shopping tab): make the container `gap: spacing.md` and `alignSelf: 'stretch'` on Buttons (or drop `alignItems:'center'`), replace `marginTop: lg` with the gap.
- shopping tab: add `accessibilityLabel` to the add Input (Input accepts any TextInput prop); no layout change needed.
- settings: add 12 dp between InlineError and the button (or put the InlineError after with marginTop sm); no other change.
- pantry search: reference implementation, no change (keep 16 outer margin because it sits in a list screen).
