**Codex evidence review (`231e294`): request changes before closing local feasibility.** Qualifications that apply to the results below (deletion spec v0.11.3):
- **Case 9 is not an exact commit-order check.** `c9_commit_order.js` sorts the commit timestamps as JavaScript dates (millisecond precision), then breaks ties by xid. That loses PostgreSQL's microsecond precision, so there may be more ties than the 2 counted in SQL, and xid order can't establish commit order. The result supports the recorded workload only. Round 3b redoes it.
- **Case 6** computes the two resolvers' payloads sequentially. It shows identical payloads, not concurrent delivery or Resend deduplication.
- **Case 7's** lost response is a simulation.
- **Case 10** tests the pure selection function, not a restore or re-application exercise.
- **The pending-only FENCE_ALL return** (v0.11.2) postdates these runs. The prototype returns every pre-existing id, so that rule is unverified.

## Discrepancies between v0.11.1 and what had to be implemented or observed

1. **ISSUE_TICKET order.** §5.1 marks ENSURE_ROW as "first step" of issue/admit, and also says issue/admit take the barrier `FOR SHARE`. Both cannot be first. Implemented barrier then ENSURE_ROW (a paused system creates no rows). State the order.
2. **Unspecified non-P0001 errors.** The error table lists `P0001` prefixes and `57014`. Observed through PostgREST: the fences' own `lock_timeout` is `55P03` (HTTP 500, after 5.0 s, before the 8 s statement timeout), and a vanished user gives `23503` (HTTP 409) from ISSUE/ADMIT/FENCE. The Edge mapping needs both: `55P03` = lock timeout -> `unknown` path, `23503` = account gone. The response for `23503` on issue/admit (not on the status path) is unspecified.
3. **D20.7b wording.** "g1's call returns STALE while g2's call is held" cannot happen if g1's call arrives while g2 holds the row: g1 blocks on the row lock, and returns STALE only after g2 commits (case 4), or fails `57014` at 8 s (case 5c). STALE-then-held only works if g1's call finished before g2's call began (case 5a). The test should name both.
4. **Previous id from FENCE_ALL.** FENCE_ALL returns only `request_id`, not whether the previous row was `pending`. A fenced row also carries a (never admitted) `request_id`, so a status resolver cannot tell a real generation from a placeholder and would emit `not_committed` for ids that never had an intent. Harmless for restore selection (no intent, so nothing is selected), but the spec's "replacing generation p" should say "pending" or FENCE_ALL should return the state.
5. **Restore selection wording.** "Intent without a generation outcome" is ambiguous (per generation or per UUID). Implemented per generation (the safe reading, fixture e1: a `not_committed` for g1 must not unblock an unresolved g2). Say so.
6. **Helper gaps in the mapping table.** For INELIGIBLE/PAUSED with `fenced_own` and a lookup error, and for `stale` with a lookup error, the table is silent; implemented as `503 unknown` with `not_committed` (g's call failed definitively). Confirm intended.
7. **Commit-order mechanism.** `track_commit_timestamp` needs a server restart (`ALTER SYSTEM` and a postmaster restart); not available on hosted without provider support. A same-transaction history log (as used here) plus ordering by xid is the portable alternative. **Controller correction:** xid order is assignment (start) order, not commit order, so it is **not** an equivalent oracle. The commit-order log stays a local test technique; v0.11.2 says so.
8. No other behavioural difference: the `GONE` branch is gone and unreachable, no `MAINTENANCE` remains, fences never read the barrier, fence_own wrapper exists.
