## Discrepancies and observations against v0.11.3

1. **Where the `23503` constraint name arrives.** §4.2 says the violation is "identified by its constraint name" but not where. Observed: in `message` only (`... violates foreign key constraint "<name>"`); `details` carries only `Key (user_id)=(...) is not present in table "users"`, which is also what any other FK to `auth.users` produces, so `details` cannot discriminate. The Edge match must be on `message` with the **exact quoted** name (a bare substring match is wrong when another constraint's name contains it). Also, the name is the PostgreSQL default (`account_deletion_requests_user_id_fkey`): the migration should name the constraint explicitly so the contract does not depend on default naming.
2. **FENCE_ALL status line is stale.** §5.1 (line 377) still says "SPECIFIED, NOT YET VERIFIED (round 3b)". The pending-only return is now verified locally (case 2); the annotation can be updated.
3. **Helper and v0.11.3 agree.** `private.pf_outcome` needed no change for the §5.1 mapping table (100-combination matrix). One reading is implicit in the table and now explicit in the helper: for INELIGIBLE and PAUSED, FENCE_OWN `gone` gives 200 `deleted` regardless of the lookup (the lookup is not consulted), and a fence lock timeout gives 503 `unknown` without a lookup.
4. **Fence timeout versus statement timeout.** FENCE_OWN's own `lock_timeout` fired after 4862 ms (`55P03`), g's blocked call after 7.8-8.7 s (`57014`): both as §4.2's tables say.
5. **D24 interaction (not a discrepancy).** An Admin API delete of a user that still has a request row is refused by the guard trigger (HTTP 500), so "the user is deleted between steps" can only happen through the function or for a row-less user; the case-4 fixture therefore uses the real function.
6. **Commit-order mechanism.** `track_commit_timestamp` could not be set by the `postgres` role (`ALTER SYSTEM` refused); it needed `supabase_admin` through `docker exec` into the fv3b db container, plus a restart. As noted in round 3, this is not available on hosted without provider support.
7. **W1 oracle uninformative (repeat).** All six forced start orders contain a fence, so no W1 admitted generation stays deletable; informative deletion coverage comes from W3 (70 committed deletions).
8. No ordering anomaly, no same-user tie, and no violation of the three D20.7 invariants was observed.
