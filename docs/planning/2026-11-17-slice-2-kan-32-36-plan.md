# Slice 2 follow-ups: pantry writes before the first load, and the low/out prompt lock — plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans (recommended here) or superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:**
- A pantry write that happens before the list's first successful read never leaves an endless spinner, a partial list or a hidden load error.
- An added pantry row never appears twice when a read already returned it.
- The low/out prompt's lock is pinned by a test, and a lost native alert can no longer leave the pantry edit form stuck.

## What exists

- **`hooks/usePantryItems.tsx`:**
  - `beginMutation()` bumps `generation`, sets loading false and **clears the error**, whether or not the list has loaded. A write before the first successful read therefore discards the in-flight read or hides `err_load_items`. `loadedScope` is never set, so the derived `loading` in `household-list.ts` stays true, and nothing re-reads.
  - `addItem` applies `setItems(prev => [item, ...prev])` without merging by id.
- **`hooks/useShoppingItems.tsx`** already has the fix for both:
  - `beginMutation()` returns `unloaded` (`loadedScope !== scope`) and keeps the error while unloaded;
  - `rereadIfUnloaded()` runs `fetchItems()` after the write settles;
  - `addItem` replaces any row with the same id.
  - Its cases are pinned in `tests/shopping-state.test.cjs` ("a write while the first read is in flight…", "a successful write after a failed load…", "a failed write after a failed load…", "a refresh that sees an added row…").
- **`tests/pantry-state.test.cjs`:** a `fixture()` with deferred reads, a fake `supabase` whose writes return `mutation(value)`, two consumers and the shared `readContract`. `row(id)` always has the name "Milk", so new cases override `name`.
- **`app/edit-item/[id].tsx`:** `onSave` runs `updateItem`, then `ask()` (the prompt) and, after a failed add, `notice()`, all inside `run()` from `hooks/useItemMutation.ts`. Save, Cancel and Delete stay disabled (`busy`) until both alerts resolve.
  - `ask()` and `notice()` resolve only on a button press or `onDismiss`.
- **React Native 0.88.1, `DialogModule.kt`:**
  - with no attached activity, `showAlert` only calls the error callback, which JS turns into `console.warn`;
  - a dialog fragment that Android restores after recreating the activity has no listener, so neither a button nor a dismissal reaches JS.
  - In both cases the promise never resolves and the form stays busy. The system back gesture still closes the screen.
  - So by analysis the lost alert is reachable, though not seen on a device yet. `app.json` locks portrait, and Expo handles the common configuration changes, so the likely triggers are an activity destroyed in the background and the "Don't keep activities" developer option.
- **`tests/edit-item-prompt.test.cjs`:**
  - `render()` with a logged `Alert.alert`, `press(text)` on the last alert and `blur()`;
  - "Save stays locked until the prompt is answered" presses Save during the prompt and checks that Delete and Cancel are disabled. No test presses Delete.
- **Docs:**
  - `docs/testing/coverage-matrix.md`: STATE-01 (Slice 1.1 table) and SHOP-LINK-01;
  - the limit line "A lost native alert (KAN-36) is still not reproducible";
  - the Slice 2 follow-up list naming KAN-36.

## Decisions

- **D1 (KAN-36 lost alert). Recommended:** while the prompt or the failure notice is pending, the pantry save has already committed, so **Cancel is enabled** and closes the screen.
  - Save and Delete stay locked.
  - Cancel is not enabled during the pantry save itself.
  - A late answer to a prompt that is still alive is ignored, because the screen has lost focus or closed (`current()`), so there is no shopping add and no second pantry write.
  - When the dialog is visible, it covers Cancel, so nothing changes for the normal path.
  - **Alternative:** record "not reproduced" and close the ticket. The ticket allows this only if the lost alert isn't judged reachable, and the analysis above says it is.
- **D2 (optional phone experiment). Recommended: yes, about 20 minutes, owner at the phone.**
  - The owner turns on "Aktivitäten nicht speichern" (Don't keep activities), so the phone destroys each activity as soon as it leaves the screen.
  - Steps:
    1. In the test APK, open the prompt (edit Milk to Low, then Save).
    2. Press Home, then return to the app.
    3. Record what happens: whether the prompt returns, and whether its buttons answer.
    4. Try Cancel, first on the pre-fix build and then on the fixed build.
  - The owner turns the option off again.
  - If the owner declines, the fix rests on the unit tests and the `DialogModule` analysis.

## Global constraints

- **KAN-32 exclusions:** no UI change, and no change to pantry duplicate rules or database constraints. The loaded-case behavior and all existing pantry tests stay unchanged.
- **KAN-36:** no change to the prompt's rule or wording.
- **Test first:**
  - each fix has failing tests first, shown red on the current code;
  - a test that pins existing behavior (Task 3) is shown red by a temporary mutation of the guard it pins, which is then reverted.
- **Device scope (D2 only):**
  - only the test APK `com.pantryflow.test` and local Supabase through the loopback proxy and `adb reverse`;
  - the owner changes phone settings, not `adb`.
- **No iOS or macOS CI.** KAN-36's iOS device check stays with PF-IOS-001.

## Review focus

1. **A re-read started by a write while unloaded loses to anything newer.** It must lose to a newer read, to a household or user change, and to a later write, through the existing generation and scope guards. It must never repopulate another household.
2. **The failed-write-after-failed-load sequence:** the re-read clears the error while it runs (`fetchItems` sets `error` to null), then shows `err_load_items` again if it fails too. A brief spinner is acceptable; an empty list without the error is not.
3. **The loaded case is unchanged:** a write on a loaded list still clears an old write error and issues no re-read (`reads.length` unchanged).
4. **Cancel during the prompt is enabled only after the pantry save resolved.** During `updateItem` it stays disabled; Save and Delete stay locked throughout. The flag must reset on every exit path: answered, failed, closed or unmounted.
5. **A late answer after Cancel** adds nothing, shows no notice and doesn't navigate a second time.

## Rulings and risks carried into execution

- **Execution mode: inline,** as in the last two packages. Four small code tasks; an Opus final review covers the branch.
- **The shopping fix is ported, not shared.** A shared helper in `household-list.ts` would also change ShoppingProvider, which KAN-32 doesn't cover.
  - Cost if wrong: two copies of a ten-line pattern. The duplication becomes a KAN-27-style cleanup.
- **The pantry update and delete re-read while unloaded too,** like shopping. No current flow can reach them, but leaving them out would keep the defect for two of three writes.
- **No "drop a missing row" for pantry.** That is a shopping behavior (`err_shopping_missing`) that KAN-32 doesn't ask for.
- **D1's Cancel doesn't settle the stuck promise.** The `run()` call of a closed screen stays pending, and its lock dies with the screen. Nothing else waits on it.
  - Cost if wrong: one unresolved promise per lost alert, freed when the screen unmounts.
- **Jira:** after the merge, KAN-32 and KAN-36 each move to Done only with the owner's approval. KAN-36's closing comment notes that the iOS check stays with PF-IOS-001, if the owner approves the comment.
